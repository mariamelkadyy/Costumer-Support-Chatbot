# RAG-Based E-commerce Customer Support Chatbot

An end-to-end NLP pipeline that classifies a customer message's language, sentiment, and intent, then answers it with a Retrieval-Augmented Generation (RAG) layer grounded in a customer-support knowledge base.

## Architecture

```
Customer message
      │
      ▼
┌─────────────────┐
│ Language Detect  │  TF-IDF + classifier → e.g. "en"
└─────────────────┘
      │
      ▼
┌─────────────────┐
│ Sentiment Model  │  fine-tuned transformer → negative / neutral / positive
└─────────────────┘
      │
      ▼
┌──────────────────────────┐
│ Rule-based smalltalk      │  regex intercept for greetings/thanks/goodbye
│ intercept (pre-filter)    │  → skips ML classifier + RAG entirely
└──────────────────────────┘
      │ (no match)
      ▼
┌─────────────────┐
│ Intent Classifier │ TF-IDF + Logistic Regression → 6 routing buckets
└─────────────────┘
      │
      ├── complaint ──────────────► canned escalation message (no RAG)
      ├── out_of_scope ───────────► canned "how can I help" message
      └── order_status / order_management /
          billing_and_refunds / account_management
                      │
                      ▼
              ┌───────────────┐
              │  RAG Pipeline  │  FAISS + sentence-transformers retrieval
              │                │  → Groq LLM (gpt-oss-20b) generation
              └───────────────┘
```

## Tech stack

| Component | Choice | Notes |
|---|---|---|
| Language detection | TF-IDF + Logistic Regression | Trained on `papluca/language-identification` |
| Sentiment/emotion | Fine-tuned transformer | Trained on `dair-ai/emotion`, mapped to 3 buckets (negative/neutral/positive) |
| Intent classification | TF-IDF + Logistic Regression | Trained on `bitext/Bitext-customer-support-llm-chatbot-training-dataset`, gold `intent` column condensed into 6 routing buckets. **Test accuracy: 99.6%** |
| Vector store | FAISS (local) | Chosen over cloud Qdrant to avoid external account setup for local grading/demo |
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2` | |
| LLM | Groq API, `openai/gpt-oss-20b` | Free tier |
| Serving | Flask | Local REST API, `/chat` and `/health` |

## Intent bucket mapping

The Bitext dataset's 27 fine-grained intents were condensed into 6 buckets for routing:

| Bucket | Source intents |
|---|---|
| `order_status` | track_order, delivery_options, delivery_period |
| `order_management` | cancel_order, change_order, place_order |
| `billing_and_refunds` | check_invoice, get_invoice, get_refund, track_refund, payment_issue, check_payment_methods, check_refund_policy, check_cancellation_fee |
| `account_management` | create_account, edit_account, delete_account, switch_account, recover_password, registration_problems, change_shipping_address, set_up_shipping_address |
| `complaint` | complaint, review, contact_customer_service, contact_human_agent |
| `out_of_scope` | newsletter_subscription |

**Design decision — smalltalk handling:** the Bitext dataset has no "greeting/goodbye/gratitude" label, so the intent classifier cannot natively recognize smalltalk (it will force-classify any greeting into whichever of the 6 trained buckets is textually closest). To handle this without introducing noisy synthetic training data, a lightweight **regex-based intercept** runs before the ML classifier: common greetings, thanks, and goodbyes are matched directly and answered with a canned response, bypassing both the intent model and the RAG pipeline. Everything else falls through to the trained classifier as normal.

**Design decision — complaint routing:** messages classified as `complaint` are routed to a fixed human-escalation message rather than an auto-generated RAG answer, regardless of detected sentiment. This was chosen over "apologize + still auto-answer" because complaints often involve account-specific issues (wrong charges, damaged goods) that a knowledge-base lookup cannot resolve, and prioritizing a real human handoff is safer than a plausible-sounding but ungrounded generated response.

## Running locally

1. Install dependencies: `pip install -r requirements.txt`
2. Set your Groq API key: `export GROQ_API_KEY="your_key_here"` (never commit real keys to the repo)
3. Run the four notebooks in order if models aren't already trained, or confirm `models/` is populated
4. Start the server: `python app.py`
5. Test:
   ```bash
   curl -X POST http://127.0.0.1:5000/chat \
     -H "Content-Type: application/json" \
     -d '{"message": "Where is my order? It'\''s been a week!"}'
   ```

## API

**POST `/chat`**
Request: `{"message": "<customer text>"}`
Response: `{"language": "...", "sentiment": "...", "intent": "...", "response": "..."}`

**GET `/health`**
Returns `{"status": "ok"}` once all four models have finished loading.

## Known limitations

- The sentiment model is trained on Twitter-style text (`dair-ai/emotion`), a domain shift from real customer-support messages; qualitative spot-checks are recommended over relying on the reported dataset accuracy alone.
- Smalltalk detection is regex-based rather than learned, so unusual phrasings of greetings/thanks may still fall through to the intent classifier.
- FAISS is used locally instead of a cloud vector DB (Qdrant), which was an allowed alternative per the assignment brief but means the knowledge base isn't shared across deployments.

## Datasets

- Language ID: [papluca/language-identification](https://huggingface.co/datasets/papluca/language-identification)
- Sentiment: [dair-ai/emotion](https://huggingface.co/datasets/dair-ai/emotion)
- Intent + RAG knowledge base: [bitext/Bitext-customer-support-llm-chatbot-training-dataset](https://huggingface.co/datasets/bitext/Bitext-customer-support-llm-chatbot-training-dataset)
